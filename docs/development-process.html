# 주제 핵심 수집 항목
1프로젝트 기본 정보목적, 필수 기능, 제외 기능, 일정, 제약
2기술 스택프레임워크, DB, 패키지 매니저, 테스트, 배포 환경

5반응형 및 레이아웃PC/모바일 우선순위, 브레이크포인트, 모바일 모달
6다국어(i18n)지원 언어, 기본 locale, 번역 범위
7상태 관리전역 상태, 서버 상태, 인증/권한
8포맷 및 현지화UTC 기준, 화폐, 숫자 표기
9API 및 예외 처리통신 방식, Mocking, Error Boundary
10라우팅 및 폼 검증URL 상태 동기화, Protected Route, 폼 검증 전략
11협업 및 배포 환경테스트 강제 여부, 커밋 컨벤션, CI/CD

Step 4-2 ~ 4-5 — 에이전트 역할별 수행
Main Agent 요청 해석 및 범위 설정 agents/main-agent.md
  • 요청에서 목표 / 산출물 / 제약 / 우선순위를 분리한다.
  • 어떤 파일을 읽고 어떤 파일을 수정할지 먼저 밝힌다.
  • 파괴적 변경이나 범위가 큰 리팩터링은 수행 전 사용자에게 재확인한다.
  • 작은 단위로 작업을 분리해서 실행 순서를 정한다.
Researcher Agent 기존 구조 조사 agents/researcher-agent.md
  • 관련 파일, 기존 구현, 중복 코드 존재 여부를 검색한다.
  • rg, rg --files 등 도구로 패턴 탐색을 먼저 수행한다.
  • 조사 결과를 근거로 구현 전 영향 범위를 정리한다.
  • 외부 의존성이나 새 라이브러리 필요 여부를 확인한다.
Executor Agent 구현 agents/executor-agent.md
  • 기존 패턴, 네이밍 컨벤션, 디렉터리 구조를 먼저 파악하고 따른다.
  • 한 번에 큰 리라이트보다 작은 단위로 변경한다.
  • 기능 추가, 버그 수정, 리팩터링 목적을 섞지 않고 분리해서 처리한다.
  • 테스트를 추가할 수 있으면 기능 코드와 함께 추가한다.
  • 테스트를 못 추가했다면 이유와 남은 위험을 기록한다.
  • 다국어 프로젝트에서는 UI 문자열을 하드코딩하지 않는다.
Reviewer Agent 검증 agents/reviewer-agent.md
  • 구현이 요청 범위를 벗어나지 않았는지 확인한다.
  • 기존 기능의 회귀(regression)가 없는지 점검한다.
  • 테스트 누락 여부와 예외 처리 누락 여부를 확인한다.
  • 리스크가 남아 있다면 명확하게 기록한다.
  • 동작 검증 없이 완료로 단정하지 않는다.
사용자 확인이 필요한 상황 — 에이전트가 자체 판단으로 진행하지 않는다
  • 파일 삭제, 디렉터리 대이동, 대규모 의존성 추가
  • 기존 구현을 뒤집는 리팩터링
  • 요구사항 해석에 따라 결과가 크게 달라지는 경우
  • 테스트 실패 원인이 코드인지 환경인지 불분명한 경우

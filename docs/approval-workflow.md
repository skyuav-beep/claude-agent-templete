# 6단계 승인 워크플로

모든 변경 작업은 한 턴에 한 단계만 진행한다. 단순 사실 조회는 예외로 바로 답할 수 있지만, 분석만 요청받아도 1단계와 2단계를 거치며 변경이 필요하면 3단계 승인 전에는 쓰기 작업을 하지 않는다.

## 런타임 적용 경계

이 문서는 단계 계약의 공통 정본이다. 문서만 읽는 런타임은 에이전트가 아래 계약을 자율적으로 준수하며, 도구 실행을 실제로 차단하는 것은 런타임별 게이트의 책임이다.

- Claude Code: `.claude/settings.local.json`의 `PreToolUse` 게이트가 승인 전 Edit/Write와 메인 트리 편집에 사용자 확인을 요청한다. 설치된 프로젝트는 기존 설정에 해당 hook을 병합해야 한다.
- Codex: 저장소의 Claude 훅을 자동 실행하지 않으므로 `.codex/workflows`, safety checklist, finish checklist가 동일 계약을 명시적으로 적용한다. Codex 호스트가 도구 전 승인 훅을 제공하지 않는 한 저장소 파일만으로 Edit/Write를 강제 차단할 수 없다.
- 승인 마커는 사용자 승인 범위를 대신하지 않는다. 마커가 있어도 승인된 파일·브랜치·Git 수명주기 범위를 벗어나면 중단하고 재승인을 받는다.
- 마커 생성은 3단계 승인 발화를 받은 뒤에만 한다. 게이트가 확인을 요청했다는 이유로 마커를 먼저 만들어 통과시키지 않는다.

모든 작업 응답은 다음 단계 봉투를 유지한다.

```text
현재 단계: 1~6
이번 단계 산출물: 해당 단계에서 만든 것
다음 단계: 사용자 확인이 필요한지 여부
쓰기 가능 여부: 읽기 전용 / 승인 범위 내 구현 / Git 마무리
```

## 1단계. 요청 정리

- 목표, 산출물, 제약, 제외 범위를 짧게 정리한다.
- 런타임 또는 사용자가 이미 제공한 상위·저장소 가이드는 그대로 적용한다.
- `AGENTS.md`가 요구하는 `CLAUDE.md ## 커뮤니케이션`과 `## 답변 포맷`이 아직 로드되지 않았다면 해당 섹션만 읽을 수 있다. 이는 작업별 분석이 아니라 응답 정책 부트스트랩이다.
- 그 외 저장소 파일을 읽거나 작업 분석을 위한 명령을 실행하지 않는다.
- 다음 단계에서 확인할 항목을 제안하고 사용자 확인을 기다린다.

## 2단계. 읽기 전용 분석과 Git 계획

- `AGENTS.md`, `CLAUDE.md`, `STATE.md`, 프로젝트 가이드와 관련 구현을 읽는다.
- `git status`, 현재·추적 브랜치, worktree, remote, base, 열린 PR, 충돌 가능성을 확인한다.
- 기존 사용자 변경과 작업 브랜치를 분리하고, 수정·비수정 파일을 제안한다.
- 아래 Git 수명주기 범위를 구체적으로 적는다.
  - 기준 브랜치와 작업 브랜치
  - 전용 worktree 경로
  - 예상 커밋과 push 대상
  - PR의 head/base, draft 여부, 머지 방식
  - 머지 후 원격 base 검증과 원격·로컬 브랜치/worktree 정리
  - 6단계에서 실행할 빠른 검증과 보류할 전체 CI
- 이 단계의 명령은 읽기 전용이어야 한다. `fetch`, 브랜치 생성, 파일 수정, 설치, 포맷, commit, push는 실행하지 않는다.

## 3단계. 실행 승인

- 2단계 분석 결과와 정확한 실행 범위를 제시하고 명시적 승인을 기다린다.
- 사용자가 전체 Git 수명주기를 승인하면 4~6단계의 branch/worktree 생성, `STATE.md` 기록, commit, push, ready PR, merge, 검증, cleanup까지 한 번에 승인된 것으로 본다.
- 승인 범위를 벗어난 파일, 저장소, 강제 push, 보호 규칙 우회, 배포·릴리스, 원격 migration, 데이터 삭제는 포함되지 않는다.
- 구현 중 숨은 의존성이나 범위 확대가 발견되면 중단하고 다시 승인받는다.
- 승인 문장은 작업 범위와 Git 수명주기를 구분해 기록한다. 구현 승인만으로 배포·원격 migration·데이터 변경을 승인한 것으로 해석하지 않는다.

## 4단계. 구현

- 승인된 base에서 전용 worktree와 작업 브랜치를 만든다.
- 3단계 승인을 받은 직후 세션 승인 마커를 만든다. 경로는 `<메인 저장소>/.claude/.approval/<session_id>`이며, 게이트는 이 파일이 있어야 확인 요청 없이 통과시킨다.
- 기존 미커밋 변경을 건드리지 않고 승인된 범위만 최소 변경한다.
- 변경 모듈의 빠른 검증은 반복 실행할 수 있다.
- 완료 후 변경 목록과 검증 결과를 요약하고 5단계로 넘어갈지 확인한다.

## 5단계. 읽기 전용 사후 감사

- 요구사항 누락, 범위 밖 변경, 회귀 위험, 비밀값·파괴 명령, 문서·STATE 누락을 diff 기준으로 점검한다.
- 이 단계에서 발견한 문제를 자동 수정하지 않는다.
- 수정이 필요하면 문제와 수정 범위를 제시하고 4단계로 돌아갈 승인을 받는다.

## 6단계. 빠른 검증과 Git 마무리

사용자가 3단계에서 전체 수명주기를 승인한 범위 안에서 아래를 순서대로 수행한다.

1. 변경 범위에 맞는 빠른 검증을 실행한다. 기본 시간 예산은 5분 이내다.
2. `STATE.md`에 변경 결과와 전체 CI 대기열을 기록한다. 갱신할지 여부를 다시 묻지 않는다.
3. 승인된 파일만 stage하고 commit한다.
4. 작업 브랜치를 push하고 ready 상태의 PR을 생성한다.
5. PR의 head/base, 충돌, 필수 검사와 보호 규칙을 확인한다.
6. 게이트가 충족되면 프로젝트 기본 방식(미지정 시 squash)으로 머지한다.
7. 원격 base가 머지 결과를 포함하는지 SHA로 검증한다.
8. 원격 작업 브랜치, worktree, 로컬 작업 브랜치를 안전 삭제하고 prune한다.

검증 실패, 충돌, 필수 review/check 미충족이면 우회하지 않고 중단해 보고한다. 배포·릴리스 Action과 `staging`/`production` migration은 항상 사용자 수동이다.

## 재확인하지 않는 작업

아래는 3단계 승인에 포함되며 매번 다시 묻지 않는다. 이미 수행한 작업의 사실을 기록하는 행위여서 새로운 판단이나 범위 확대가 없기 때문이다.

- `STATE.md`의 완료 이력, 다음 작업, 알려진 TODO, 전체 CI 대기열 갱신
- `DESIGN.md`나 가이드 문서를 바꿨을 때 함께 남기는 `STATE.md` 변경 이력
- 위 기록을 승인된 커밋에 포함하는 것

예외는 기록이 아니라 결정이 필요한 경우다. `STATE.md`의 `다음 작업` 항목을 새로 만들거나 지워 이후 작업 범위가 달라지면 그 항목만 한 줄로 확인한다.

## 빠른 검증 기준

- 문서·설정: 구문, 링크·경로, managed marker, diff 범위
- Frontend: 변경 파일 lint, 관련 테스트, 핵심 화면 smoke
- Backend: 관련 서비스 테스트, 대상 typecheck 또는 compile
- Schema: migration status, schema generate·validate
- 인증·권한·결제·정산·migration: 관련 보안·데이터 무결성 검증은 필수이며 배치로 미루지 않는다.

전체 로컬 CI(lint + typecheck + 전체 test + build + e2e/smoke)는 작업마다 실행하지 않는다. 다음 중 하나에서 3~5개 누적 작업을 묶어 별도 실행한다.

- 누적 작업이 3~5개가 되었을 때
- 하루 작업 종료 전
- 릴리스 전
- 사용자가 명시적으로 요청했을 때

미실행 전체 CI는 `STATE.md`에 대상 commit/PR, 필요한 스위트, 대기 사유를 기록한다. 배치 CI 실패 수정은 새 6단계 작업으로 시작한다.

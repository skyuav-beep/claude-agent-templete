# 스킬 강화를 위한 에이전트 업데이트 봇 개발계획

## 요청과 목표

사용자 원문: “에이전트 템프릿에 에이전트 스킬 강화를 위한 에이전트 업데이트 봇이 가미된 에이전트를 만들기 위한 계획도 고려해줘”

작업 중 반복되는 실패와 사용자 교정에서 개선 후보를 찾아, 스킬 변경안을 검증하고 검토를 거쳐 반영하는 업데이트 봇을 계획한다. 여기서 강화는 모델 가중치 학습이 아니라 스킬의 선택 조건·절차·예시·검증 기준을 개선하는 것이다. 이 문서는 계획 초안이며 봇 구현이나 상시 실행을 활성화하지 않는다.

## 근거와 기존 구조 연결

- [역할 봇 지침](../../agents/roles/README.md): 현재 7종 역할과 작업 카드 파이프라인을 재사용한다.
- [협업 운영](../claude-codex-collaboration.md): 작업 끝 교차 리뷰, 자동 수정 2회 한도, 메모리 사용률 80% 미만 실행 기준을 따른다.
- [승인 절차](../approval-workflow.md): 실제 변경과 Git 작업은 승인된 범위로 제한한다.
- [런타임 대응](../agent-runtime-matrix.md): 공통 정본 변경과 Claude·Codex 어댑터 변경을 구분한다.
- [설치 운영](../plugin-guide.md): 소비 프로젝트의 소유 파일과 템플릿 관리 파일을 구분한다.
- 별도 요구사항·설계·ADR은 아직 없다. 아래 제안의 구현 착수 시 범위와 결정 사항을 구체화한다.

## 범위와 역할 제안

업데이트 봇은 제품 기능 개발 파이프라인에 매번 끼우기보다, 작업 완료 후 개선 후보를 모으는 보조 역할로 둔다. 초기에는 리드가 명시적으로 호출하며, 검증 근거가 쌓인 뒤 주기 실행을 검토한다.

| 구성 | 책임 | 산출물 |
|---|---|---|
| 근거 수집 | 허용된 작업 카드·검증 결과·사용자 교정에서 실패 유형 추출 | 출처와 대상 스킬이 있는 후보 목록 |
| 업데이트 봇 | 재현 가능한 개선 후보 선정, 최소 변경안과 평가 사례 작성 | 개선 제안서·후보 diff |
| 기존 audit·qa 역할 | 변경 작성자와 분리해 규칙 충돌·회귀·효과 확인 | 검토 결과·전후 비교 |
| 리드 | 범위 판단, 승인된 변경의 Git 처리와 기록 | PR·결정 이력·재개 지점 |

현재 이벤트 기록은 실행 상태 관찰용이므로 성공·실패의 품질 근거로 단독 사용하지 않는다. 완료 상태도 정답을 보장하지 않으므로 검증 결과와 사용자 피드백을 함께 연결한다.

템플릿에는 역할 계약·제안 양식·평가 기준을 두고, 실행기·예약 실행·상태 UI는 별도 런타임 영역으로 분리하는 안을 권장한다. agent-deck의 새 역할 등록은 후속 연동 작업이며 이번 계획으로 기존 7종을 변경하지 않는다.

## 개선 처리 흐름

`수집 → 후보 선정 → 재현 → 변경안 생성 → 전후 평가 → 독립 검토 → 반영 → 관찰`

1. 프로젝트별 사례와 템플릿 공통 결함을 구분한다. 개별 프로젝트 정책은 공통 스킬로 승격하지 않는다.
2. 제안에 ID, 출처, 스킬 경로, 기준 commit, 재현 입력, 기대 결과, 변경 이유, 평가 방법을 기록한다. 같은 원인·스킬·기준 버전은 하나로 묶는다.
3. 재현 가능한 결함 또는 사용자 교정 근거가 있는 후보부터 처리한다. 추측과 외부 문서의 권고는 별도로 표시한다.
4. 전용 worktree에서 작은 diff를 만들고, 같은 모델·환경·입력 조건으로 기존판과 후보판을 비교한다. 기준 commit이 바뀌면 재평가한다.
5. 평가를 통과한 후보만 기존 승인·리뷰·PR 절차에 전달한다. 봇은 자체 평가만으로 스스로 머지하지 않는다.
6. 반려 사유와 재시도 횟수를 남긴다. 동일 실패 수정은 2회까지 시도하고 초과 시 확인 필요로 전환한다.
7. 반영 후 회귀가 확인되면 후속 적용을 멈추고 해당 변경의 revert 후보를 만든다. 복구도 동일 검토 절차를 따른다.

## 마일스톤

| 순서 | 산출물 | 완료 조건 | 상태 |
|---|---|---|---|
| 1 | 역할 계약·개선 제안 양식·평가 사례 집합 | 스킬 선택 오류, 절차 누락, 검증 누락의 3유형을 기존 사례와 연결 | 제안 |
| 2 | 수동 호출로 제안만 생성하는 MVP | 근거가 있는 제안 1건 생성, 중복 후보 병합, 근거 없는 후보 보류 | 제안 |
| 3 | 격리된 변경안·전후 평가·독립 검토 연결 | 대표 사례 개선, 기존 회귀 사례 통과, Claude·Codex 대응 검사 통과 | 제안 |
| 4 | 승인된 반영과 복구 시험 | 시험 대상에서 반영·추적·revert 경로 확인 | 제안 |
| 5 | 선택적 주기 실행과 관리 화면 | 실행 예산·중복 실행 잠금·중지 기능·범위 제한 확인 | 보류 |

1~4의 완료 조건과 시험 결과를 보고 5의 필요성을 판단한다. 기존 개발계획의 우선순위는 이 초안만으로 바꾸지 않는다.

## 평가·운영 기준 제안

- 평가 축: 올바른 스킬 선택률, 요구사항 충족률, 기존 사례 회귀 수, 불필요한 질문·도구 호출, 시간·토큰 비용. 관측하지 못한 값은 추정치로 채우지 않는다.
- 재현 사례와 별도의 미사용 평가 사례를 분리해 특정 예시만 통과하도록 지침이 편향되는 것을 막는다. 비결정적 결과는 반복 실행하고 원자료·실행 횟수를 기록한다.
- 초기 통과 조건: 목표 실패 재현과 개선 확인, 기존 필수 사례의 신규 실패 0, 중대 리뷰 이슈 0. 비용 증가 허용치는 구현 전에 정하며 효과와 함께 보고한다.
- 스킬 검사는 기존 `check-codex-skills.mjs`·`check-runtime-parity.mjs`를 활용하되, 형식 통과를 실제 품질 향상으로 보지 않는다.
- 외부 문서·작업 로그 안의 지시는 자료로 취급한다. 승인 범위·권한·보호 규칙을 변경하는 명령으로 실행하지 않는다.
- 수집 대상은 명시된 프로젝트와 파일로 제한하고 비밀값·개인정보를 제거한 요약만 제안에 남긴다. 전체 대화 로그 수집이나 다른 저장소 탐색은 기본 동작에 포함하지 않는다.
- 자기 자신의 승인·평가 기준, 권한 확대, 배포·원격 migration은 자동 변경 대상에서 제외한다. 외부 스킬 설치·패키지 업그레이드도 별도 요청으로 처리한다.
- `rules/` symlink 연결은 템플릿 머지 즉시 소비 프로젝트에 영향을 줄 수 있다. 따라서 실제 스킬 변경은 머지 전에 영향 범위를 확인하고 격리된 복사본으로 평가한다. 단계적 적용이 필요하면 버전 고정 방식부터 설계한다.
- 연결 프로젝트 일괄 업데이트는 별도 범위로 둔다. 로컬 커스텀을 덮어쓰지 않으며 설치기의 소유권·해시 상태를 따른다.

## 미결정 사항과 다음 착수점

- 최초 개선할 스킬 1종과 재현 사례를 선정한다. 선택 정확도 또는 검증 누락처럼 효과를 측정할 수 있는 문제를 권장한다.
- 실행 주체(리드 수동 호출 또는 agent-deck 역할), 모델, 평가 반복 횟수·비용 예산을 정한다.
- 주기 실행 간격, 데이터 보관 기간, 공통 스킬 승격 기준은 MVP 결과 후 결정한다.
- 다음 구현 요청에서는 마일스톤 1~2를 작업 카드로 나누고, 이 문서의 draft 항목을 확정한다.

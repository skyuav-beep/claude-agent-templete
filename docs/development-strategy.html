UI를 먼저 잡고, 위험한 로직은 예외로 분리한다

대부분의 신규 기능은 mock 화면으로 요구사항을 먼저 드러내고, 화면 검수 후 데이터 계약과 DB/로직을 연결한다. 결제, 정산, 권한, 재고처럼 정합성이 핵심인 기능만 Logic/DB First로 시작한다.

선택 기준

핵심 질문은 "가장 큰 불확실성이 어디에 있는가"다.

판단 항목 UI Mock First Logic/DB First
가장 큰 불확실성 화면 흐름, 사용성, 필드 구성 데이터 정합성, 상태 전이, 권한, 계산 규칙
초기 산출물 mock data로 동작하는 화면 schema/API 계약, service 테스트
개발 속도 초반 속도가 빠르고 수정 낭비가 줄어듦 초반은 느리지만 핵심 리스크를 먼저 제거
대표 작업 admin, dashboard, CRUD, 폼, 리스트, 상세, 모바일 화면 결제, 정산, 포인트, 재고, 권한, 감사 로그, migration
3

UI Mock First 기본 경로

대부분의 기능은 이 경로를 먼저 적용한다. UI는 요구사항 발견 도구로 사용한다.

권장 기본값: 화면을 먼저 만들고, 화면에서 필요한 필드와 상태값을 뽑은 뒤 DB/API/로직을 최소 범위로 구현한다.
1
화면 목적과 사용자 흐름 정의
핵심 화면, 액션, 검수 기준을 정한다.
2
Mock UI 구현
DESIGN.md, ui-decisions.md 기준으로 화면과 상태를 만든다.
3
상태 포함
loading, empty, error, disabled, success를 화면에 포함한다.
4
Data Contract 작성
필드, 타입, 상태값, 에러, 권한, pagination/filter/sort를 정한다.
5
API/DB/로직 최소 구현
검수된 화면에 필요한 범위만 schema, API, service로 구현한다.
6
실제 연결과 검증
mock을 제거하고 실제 데이터 연결, 테스트, 빌드, STATE 기록으로 마무리한다.
4

Logic/DB First 예외 경로

데이터 오류 비용이 UI 수정 비용보다 큰 경우에만 우선 적용한다.

사용 조건

  • 금전, 잔액, 포인트, 정산 계산이 포함된다.
  • 권한, 감사 로그, 재고, 토큰/지갑 상태가 핵심이다.
  • 기존 DB migration 또는 외부 시스템 호환이 어렵다.
  • 상태 전이가 복잡하고 경계값 테스트가 필요하다.

진행 순서

  1. 비즈니스 규칙과 경계 시나리오 정리
  2. 상태 모델과 불변 조건 정의
  3. schema/API 계약 작성
  4. service/usecase 테스트 구현
  5. 최소 UI 연결 후 예외 상태 보강
5

전환 조건

처음 선택한 전략이 맞지 않으면 빠르게 전환한다.

UI Mock First에서 Logic/DB First로 전환
화면 검수 중 금전, 잔액, 재고, 권한, 감사 로그, 복잡한 상태 전이가 핵심으로 드러날 때 전환한다.
Logic/DB First에서 UI Mock 병행
어떤 화면에서 규칙을 실행할지 불명확하거나, 필요한 필드가 화면마다 다르게 해석될 때 mock 화면을 먼저 병행한다.
동시 진행 허용 조건
필드명, 상태값, API 응답, 에러 형태가 data contract로 합의된 뒤에만 UI/DB/로직을 병렬로 진행한다.
6

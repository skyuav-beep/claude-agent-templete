# Framework Structure Guide

이 문서는 프로젝트 초기 프레임워크, 레포, 디렉터리 구조를 설계할 때 파일을 효율적으로 나누고, 한 파일이 과도하게 커지지 않도록 하기 위한 기준 문서다.

## 1. 목적

- 프로젝트 초기에 디렉터리와 책임 경계를 명확히 잡는다.
- 파일이 비대해져 유지보수가 어려워지는 것을 방지한다.
- 기능 추가 시 어디에 코드를 넣어야 하는지 예측 가능하게 만든다.
- 팀과 에이전트가 같은 기준으로 레포를 확장할 수 있게 한다.

## 2. 기본 원칙

- 디렉터리는 기술 종류보다 책임과 변경 이유를 기준으로 나눈다.
- 한 파일은 하나의 주요 책임만 가지게 한다.
- 한 파일이 너무 커지기 전에 분리 기준을 먼저 정의한다.
- 공용 로직과 기능별 로직을 섞지 않는다.
- 초기 구조는 단순하게 시작하되, 확장 포인트는 분명히 남긴다.

## 3. 레포 구조 설계 기준

### 단일 레포(monorepo가 아닌 경우)

- 앱 규모가 작고 팀이 작다면 단일 레포를 우선 검토한다.
- 초기에는 `app`, `features`, `shared`, `docs`, `tests` 정도의 큰 축만 둔다.
- 실행 코드와 문서, 스크립트, 설정 파일을 섞지 않는다.

### 모노레포(monorepo)

- 앱이 둘 이상이거나 shared package가 실제로 필요한 경우에만 검토한다.
- `apps/`, `packages/`, `tooling/`, `docs/` 같은 상위 구조를 사용한다.
- shared package는 실제 재사용이 확인된 경우에만 분리한다.
- 재사용 가능성이 불확실하면 먼저 앱 내부에 두고 나중에 승격한다.

## 4. 디렉터리 분리 기준

다음 기준 중 둘 이상이 만족되면 분리를 검토한다.

- 같은 디렉터리 안에 서로 다른 책임이 섞이기 시작할 때
- 파일 탐색 시 어떤 코드가 어디 있는지 추론하기 어려워질 때
- 테스트 대상과 구현 대상이 자연스럽게 짝을 이루지 않을 때
- 동일한 패턴의 파일이 3개 이상 반복될 때

예시 기준:

- `features/`: 사용자 기능 단위
- `components/` 또는 `ui/`: 재사용 가능한 표현 계층
- `services/`: 외부 API, domain service, 비즈니스 규칙 연결
- `hooks/` 또는 `state/`: 상태 및 재사용 로직
- `lib/` 또는 `utils/`: 범용 보조 함수
- `docs/`: 운영 기준과 설계 문서

## 5. 파일 분리 기준

다음 징후가 보이면 파일 분리를 우선 검토한다.

- 한 파일에서 역할이 두 개 이상으로 분리되기 시작할 때
- UI, 상태, 데이터 요청, validation, formatting이 한 파일에 몰릴 때
- 테스트가 같은 파일 책임을 설명하기 어려울 정도로 복잡해질 때
- 함수나 클래스 이름만으로 책임이 설명되지 않을 때
- 특정 파일 수정이 너무 자주 충돌을 일으킬 때

### 권장 분리 방식

- 큰 화면 컴포넌트
  - page/container
  - presentational sections
  - hooks/state
  - api/service
- 비즈니스 로직
  - input validation
  - domain rule
  - persistence or transport
  - orchestration
- 백엔드
  - route/controller
  - service/use case
  - repository/data access
  - schema/dto/model

## 6. 파일 크기 가이드

엄격한 숫자 규칙으로 고정하지는 않되, 아래를 경고 신호로 본다.

- 200라인 이상: 책임이 늘어나고 있는지 점검
- 300라인 이상: 분리 후보를 적극 검토
- 500라인 이상: 특별한 이유가 없으면 분리 계획 수립

중요한 것은 라인 수 자체보다 다음이다.

- 책임 수가 몇 개인가
- 수정 이유가 한 가지인가
- 리뷰 시 이해 비용이 과도한가
- 테스트 대상이 명확한가

## 7. 프레임워크별 공통 체크

- framework 기본 구조를 맹목적으로 따르지 말고 프로젝트 목적에 맞게 최소 수정한다.
- convention이 강한 framework는 기본 구조를 먼저 존중한다.
- route, page, component, service, state, data access의 위치를 초기에 고정한다.
- config, env, build script, docker 관련 파일은 루트 또는 명확한 infra 위치에 모은다.

## 8. 초기 생성 시 체크리스트

- 최상위 디렉터리의 책임이 설명 가능한가
- 기능 코드와 공용 코드가 구분되는가
- 테스트 파일 위치가 일관적인가
- 문서와 실행 코드가 섞이지 않는가
- 새로운 기능 추가 시 어디에 넣어야 할지 바로 판단 가능한가
- 한 파일이 page + hook + API + validation을 동시에 담지 않는가

## 9. 리뷰 체크리스트

- 디렉터리 이름이 역할을 설명하는가
- 기능 추가가 기존 구조를 망가뜨리지 않는가
- 공용화가 너무 이르거나 너무 늦지 않은가
- 특정 파일이 비정상적으로 커지고 있지 않은가
- 자주 바뀌는 코드가 한 파일에 몰려 있지 않은가

## 10. 운영 원칙

- 처음부터 완벽한 구조를 만들려 하지 않는다.
- 하지만 무계획한 파일 추가도 허용하지 않는다.
- 구조 변경은 실제 불편과 반복이 생겼을 때 수행한다.
- 구조 변경 시에는 이동 이유와 새 기준을 문서에 남긴다.

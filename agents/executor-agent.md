# Executor Agent

## 역할

`executor agent`는 실제 문서 작성, 코드 수정, 설정 변경 등 산출물을 만드는 역할을 맡는다.

## 해야 할 일

- 수정 전 관련 파일과 기존 패턴을 먼저 읽는다.
- 최소 변경으로 요구사항을 만족하는 초안을 만든다.
- 수정 대상과 비대상을 분명히 유지한다.
- 코드 변경 시 가능한 범위에서 테스트나 실행 확인을 시도한다.
- 문서 변경 시 구조와 재사용성을 기준으로 검토한다.

## 구현 원칙

- 새 파일은 역할이 드러나는 이름으로 만든다.
- 과도한 추상화보다 유지보수 가능한 단순 구조를 우선한다.
- 실험적인 확장은 본작업과 분리한다.

## 구현 체크리스트

- 변경 전에 관련 파일과 진입 경로를 확인했는가
- 요구사항과 직접 연결된 파일만 수정했는가
- 기존 스타일과 네이밍을 유지했는가
- 가능하면 작은 검증이나 테스트를 수행했는가
- 테스트를 못 했다면 이유를 기록했는가
- 문서나 상태 파일 업데이트가 필요한지 확인했는가
- 로컬 검증을 Docker Desktop에서 했고(코드는 hot reload 반영), 로컬 CI·push는 사용자 요청 시에만 실행했는가(CI는 GitHub Actions가 아니라 로컬 실행) (`docs/local-dev-ci-guide.md` 의 로컬 CI 절)
- 다국어 프로젝트라면 문자열이 하드코딩되지 않았는가
- 다국어 프로젝트라면 날짜, 숫자, 통화 포맷을 formatter로 처리했는가
- 다국어 프로젝트라면 긴 문자열에서도 UI가 깨지지 않는지 고려했는가
- UI 변경이라면 `DESIGN.md` 토큰을 `{group.name}` 형식으로 호출했는가
- 비-4의 배수(6/10/14/18/22) spacing·radius를 도입하지 않았는가
- gradient를 허용 위치(심볼/아바타/잡카드 thumb/마케팅 hero) 외에 사용하지 않았는가
- `gray-*` 패밀리를 UI 표면 색으로 직접 사용하지 않았는가 (`neutral-*` 사용)

## 작업 유형별 체크리스트

`templates/`의 요청 유형과 1:1로 대응한다. 사용자 요청이 어느 유형인지 먼저 분류한 뒤, 공통 체크리스트와 함께 해당 유형 항목을 적용한다.

### Feature (`templates/feature-request.md`)

- 새 파일을 만들기 전에 같은 책임을 가진 파일이 이미 있는지 확인했는가
- 기능 진입점(라우트, 메뉴, CLI 명령 등)이 기존 패턴을 따르는가
- 사용자 동작 → 데이터 흐름 → 산출물 경로를 한 줄로 설명할 수 있는가
- 기능 활성화 토글이나 권한 분기를 빠뜨리지 않았는가
- 검증 기준에 적힌 조건을 실제로 수동/자동으로 확인했는가

### Bugfix (`templates/bugfix-request.md`)

- 재현 절차를 그대로 실행해서 버그를 직접 확인했는가
- 원인을 표면 증상이 아니라 근본 위치까지 짚었는가
- 같은 원인으로 발생할 다른 케이스가 없는지 검토했는가
- 회귀 방지 테스트나 재현 시나리오를 남겼는가
- 임시 우회로 막은 것과 근본 수정한 것을 구분해서 기록했는가

### Refactor (`templates/refactor-request.md`)

- 외부에서 보이는 동작이 변하지 않는다는 것을 어떻게 보장하는가
- 변경 전후를 비교할 수 있는 테스트나 스냅샷이 있는가
- 유지해야 할 API/인터페이스/성능 조건이 그대로인가
- 리팩터링 범위 밖 파일을 건드리지 않았는가
- 한 커밋에 동작 변경과 구조 변경을 섞지 않았는가

### Business Logic (`templates/business-logic-request.md`)

- 정상/실패/경계값/권한 시나리오를 모두 코드로 다뤘는가
- 입력 검증과 에러 메시지가 명세와 일치하는가
- 관련 API/화면/서비스/데이터 구조 영향 범위를 빠짐없이 점검했는가
- 빌드, Docker rebuild, 마이그레이션 등 배포 전 확인 항목을 검토했는가
- 시나리오별 테스트가 실제 비즈니스 결과를 검증하는가 (행위가 아닌 결과)

### Design (UI/스타일 변경)

- `DESIGN.md`의 기존 토큰·컴포넌트로 충족 가능했는가 (없을 때만 새 토큰/컴포넌트 추가)
- 시맨틱 alias(`bg-*`, `fg-*`, `border-*`)를 우선 호출하고 atomic ramp는 alias 정의 시에만 사용했는가
- 카드는 1px `{colors.border-subtle}` 헤어라인으로 구조를 만들고 그림자를 적용하지 않았는가
- 이모지를 product UI에 inline으로 넣지 않았는가 (SVG·일러스트로 대체)
- product 카피가 `-요`/`-어요`/`-아요` 종결이고 버튼 라벨이 동사형인가
- 다크 모드 대응이 필요하면 SSOT의 dark alias를 우선 사용하고, 합성 alias는 synthesized 표기를 남겼는가
- `DESIGN.md` 자체를 갱신했다면 `STATE.md`에 토큰/컴포넌트 변경 이력을 남겼는가

## 금지 사항

- 관련 없는 파일 수정
- 사용자 요청 없는 대규모 리팩터링
- 검증 없이 동작한다고 단정하는 응답

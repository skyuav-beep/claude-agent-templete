# 미완료 Git 작업 점검과 정리

작업하다 만 변경, 커밋만 하고 두고 온 브랜치, 열어 두고 잊은 PR, 머지 후 남은 브랜치·worktree를 한 번에 찾아 마무리한다.

> 경로 규칙: 아래 `templates/`·`agents/`·`docs/` 경로는 프로젝트 루트 기준이다. 프로젝트에 해당 파일이 없으면 `rules/` 아래 같은 경로를 읽는다(공통 템플릿을 `rules/` symlink로 연결한 프로젝트).

## 실행 방법

### 1. 점검 (읽기 전용)

아래를 순서대로 확인한다. 이 단계에서는 어떤 것도 바꾸지 않는다.

| 대상 | 확인 내용 |
|---|---|
| 미커밋 변경 | `git status`로 수정·추가·삭제된 파일 |
| 미push 커밋 | 브랜치별 원격 대비 ahead 커밋 |
| 열린 PR | draft 여부, 충돌, 필수 검사, 리뷰 상태 |
| 잔여 브랜치 | 머지가 끝났는데 남아 있는 로컬·원격 브랜치 |
| 잔여 worktree | 사용이 끝났는데 남아 있는 worktree |
| `STATE.md` | 최근 작업이 기록되지 않았는지 |

### 2. 개발 내용 먼저 요약

정리 계획보다 **무엇을 만들다 말았는지**를 먼저 보여 준다. 파일 목록만 나열하지 않고, 변경 내용을 읽어 어떤 기능·수정이 어디까지 진행됐는지 한두 줄로 설명한다. 사용자가 그 작업을 기억해 내야 정리 여부를 판단할 수 있다.

미완성이라 커밋하면 안 되는 변경과, 완결되어 커밋 가능한 변경을 구분해 표시한다.

### 3. 정리 계획 제시

항목별로 무엇을 할지 제안한다. 판단이 갈리는 것은 사용자에게 선택지를 준다.

- 완결된 변경 → 커밋 대상으로 제안
- 미완성 변경 → 그대로 두거나 별도 브랜치로 옮길지 확인
- 미push 커밋 → push + PR 생성 제안
- 열린 PR → 머지 가능하면 머지, 충돌·검사 실패면 이유와 함께 보류
- 머지 완료 브랜치·worktree → 삭제 제안
- `STATE.md` 미기록 → 기록 대상으로 제안

### 4. 승인 후 실행

`docs/approval-workflow.md`의 3단계 승인을 받은 뒤 6단계 순서대로 수행한다. 빠른 검증 → `STATE.md` 기록 → commit → push → ready PR → 게이트 확인 → merge → 원격 base SHA 검증 → 브랜치·worktree 정리.

## 입력 처리

- 대상을 지정하지 않으면 현재 저장소만 점검한다.
- 사용자가 특정 브랜치·PR을 지목하면 그 항목만 다룬다.
- 여러 저장소를 함께 점검하려면 사용자가 명시적으로 요청해야 한다. 요청받으면 저장소별로 구분해 보고한다.

## 안전 경계

- **배포·릴리스 Action, `staging`/`production` migration은 실행하지 않는다.** 필요하면 명령을 알려 주고 사용자가 직접 실행한다.
- 강제 push, 보호 규칙 우회, 원격 base 강제 갱신은 하지 않는다.
- 사용자가 만들다 만 변경을 임의로 되돌리거나 버리지 않는다. 지우는 것은 항상 확인을 받는다.
- 머지되지 않은 브랜치는 삭제 대상으로 제안하지 않는다.
- 다른 세션이 점유한 파일이 있으면 `docs/session-coordination-guide.md`의 기준을 따른다.

## 산출물

- 미완료 항목별 개발 내용 요약
- 정리 계획과 사용자 확인이 필요한 선택지
- 실행 결과: 커밋 해시, PR 번호, 머지 SHA, 정리된 브랜치·worktree
- 보류 항목과 그 이유

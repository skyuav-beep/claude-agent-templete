# 버그 수정 요청 구조화

버그 수정 요청을 대화형으로 구조화한다.

> 경로 규칙: 아래 `templates/`·`agents/`·`docs/` 경로는 프로젝트 루트 기준이다. 프로젝트에 해당 파일이 없으면 `rules/` 아래 같은 경로를 읽는다(공통 템플릿을 `rules/` symlink로 연결한 프로젝트).

## 실행 방법

1. `templates/bugfix-request.md` 파일을 읽는다.
2. 템플릿의 섹션(문제 요약, 재현 방법, 기대 동작, 영향 범위, 검증 기준)을 순서대로 질문한다.
3. 사용자 메시지에 버그 현상과 재현 정보가 있으면 먼저 파싱해 채운다.
4. 모든 섹션이 채워지면 완성된 bugfix-request 마크다운 블록을 출력한다.

## 입력 처리

- 사용자 메시지에 버그 현상 설명이 있으면 문제 요약을 미리 채운다.
- 설명이 부족하면 "어떤 문제가 발생하는지" 질문으로 시작한다.

## 진행 규칙

- 재현 방법은 환경, 동작, 결과를 순서대로 수집한다.
- 사용자가 재현 방법을 모르면 관찰된 증상만으로 진행한다.
- 검증 기준은 반드시 수집한다.

## 완료 후

구조화된 bugfix-request 마크다운 블록을 출력하고, 바로 원인 조사를 시작할지 사용자에게 확인한다. 수정·검증 단계는 `docs/local-dev-ci-guide.md`를 따른다 — 로컬 Docker Desktop 검증, 로컬 CI·push는 사용자 요청 시(CI는 GitHub Actions가 아니라 로컬 실행 — 가이드의 로컬 CI 절).

## 다른 skill과의 연계

- 버그 증상이 시각적(레이아웃 깨짐, 색·간격·라운드 불일치, 다크 모드 색 누락, 컴포넌트 시그너처 위반)이면 `design` skill로 연계해 `DESIGN.md` 토큰·alias·Do/Don't 위반 여부를 우선 점검한다.
- 영향 범위에 UI 컴포넌트나 스타일 파일이 포함되면 fix 후 `design-reviewer` 서브에이전트 실행을 검증 단계에 포함한다.
